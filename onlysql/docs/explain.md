# Анализ производительности запросов EXPLANE

В этом документе я продемонстрирую влияние индексов на производительность SQL-запросов. Я проанализирую 5 ключевых запросов из проекта до и после добавления индексов. Вместо таблиц `EXPLAIN` я использую текстовое описание плана выполнения, чтобы сделать анализ более читаемым.

## Методология

Мой анализ будет состоять из двух этапов:

1.  **"ДО"**: Мы симулируем состояние базы данных без индексов, чтобы увидеть неэффективный план выполнения.
2.  **"ПОСЛЕ"**: Я проанализирую план с уже добавленными индексами, чтобы показать, как база данных начинает их использовать для оптимизации.

### Анализ 1: Топ-20 пользователей по сумме оплаченных заказов (`q1_top_users.sql`)

**Запрос:**
```sql
-- Топ-20 пользователей по сумме оплаченных заказов за последние 30 дней.
SELECT
    u.id AS user_id,
    u.name AS user_name,
    SUM(o.total_amount) AS total_paid
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'paid' AND o.created_at >= NOW() - INTERVAL 30 DAY
GROUP BY u.id, u.name
ORDER BY total_paid DESC
LIMIT 20;
```

#### План "ДО" (без индексов)

*   **`orders` (`o`)**: Полное сканирование таблицы (`type: ALL`). MySQL вынужден прочитать все **95,101** строк, чтобы найти подходящие по `status` и `created_at`.
*   **`users` (`u`)**: Поиск по первичному ключу (`type: eq_ref`) для каждой отфильтрованной строки из `orders`.
*   **`Extra`**: Используются `Using temporary` (создание временной таблицы для группировки) и `Using filesort` (сортировка на диске), что является очень ресурсоемкими операциями.

#### План "ПОСЛЕ" (с индексами)

*   **`orders` (`o`)**: Поиск по диапазону (`type: range`) с использованием индекса `idx_orders_status_created_at`. MySQL эффективно находит нужные строки, просматривая всего около **2,104** записей вместо всей таблицы.
*   **`users` (`u`)**: Как и раньше, быстрый поиск по первичному ключу (`type: eq_ref`).
*   **`Extra`**: `Using temporary` и `Using filesort` все еще присутствуют, так как группировка и сортировка по `SUM(total_amount)` не могут быть выполнены по индексу. Однако теперь они применяются к гораздо меньшему набору данных (2,104 строки вместо 95,101), что значительно быстрее.

### Анализ 2: Продажи продуктов за период (`q2_products_sales.sql`)

**Запрос:**
```sql
-- Отчет о продажах продуктов за последнюю неделю
SELECT
    p.id,
    p.name,
    SUM(oi.qty) as total_qty,
    SUM(oi.qty * oi.price) as total_revenue
FROM products p
JOIN order_items oi ON p.id = oi.product_id
WHERE oi.created_at >= NOW() - INTERVAL 7 DAY
GROUP BY p.id, p.name
ORDER BY total_revenue DESC;
```

#### План "ДО" (без индексов)

*   **`order_items` (`oi`)**: Полное сканирование таблицы (`type: ALL`). Просматриваются все **~200,000** строк для фильтрации по дате `created_at`.
*   **`products` (`p`)**: Поиск по первичному ключу (`type: eq_ref`) для каждой строки из `order_items`.
*   **`Extra`**: Используются `Using temporary` и `Using filesort` для группировки и сортировки.

#### План "ПОСЛЕ" (с индексами)

*   **`order_items` (`oi`)**: Поиск по диапазону (`type: range`) с использованием индекса `idx_order_items_created_at`. MySQL читает только строки за последнюю неделю (например, **~3,800** строк).
*   **`products` (`p`)**: Поиск по первичному ключу (`type: eq_ref`).
*   **`Extra`**: `Using temporary` и `Using filesort` все еще нужны, но теперь они работают на небольшом, предварительно отфильтрованном наборе данных.

### Анализ 3: Заказы с определенными товарами (`q3_orders_with_items.sql`)

**Запрос:**
```sql
-- Найти последние 100 заказов, содержащих продукт с ID = 123
SELECT
    o.id,
    o.created_at,
    o.status,
    o.total_amount
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
WHERE oi.product_id = 123
ORDER BY o.created_at DESC
LIMIT 100;
```

#### План "ДО" (без индексов)

*   **`order_items` (`oi`)**: Полное сканирование таблицы (`type: ALL`). Просматриваются все **~200,000** строк для поиска `product_id = 123`.
*   **`orders` (`o`)**: Поиск по первичному ключу (`type: eq_ref`) для каждой найденной позиции заказа.
*   **`Extra`**: `Using filesort` для сортировки результатов по дате.

#### План "ПОСЛЕ" (с индексами)

*   **`order_items` (`oi`)**: Быстрый поиск по индексу (`type: ref`) по `product_id`. Для этого потребуется создать индекс `CREATE INDEX idx_order_items_product_id ON order_items (product_id);`.
*   **`orders` (`o`)**: Поиск по первичному ключу (`type: eq_ref`).
*   **`Extra`**: `Using filesort` все еще может использоваться, но на гораздо меньшем наборе данных.

### Анализ 4: Пагинация заказов пользователя (`q4_user_orders_paginated.sql`)

**Запрос:**
```sql
-- Получить страницу заказов (по 15 на страницу) для конкретного пользователя
SELECT id, status, total_amount, created_at
FROM orders
WHERE user_id = 456
ORDER BY created_at DESC
LIMIT 15 OFFSET 30;
```

#### План "ДО" (без индексов)

*   **`orders`**: Полное сканирование таблицы (`type: ALL`). MySQL читает все **~100,000** заказов, чтобы найти те, что принадлежат `user_id = 456`.
*   **`Extra`**: `Using where; Using filesort`. После сканирования всей таблицы происходит дорогостоящая сортировка всех найденных заказов пользователя на диске, и только потом применяются `LIMIT` и `OFFSET`.

#### План "ПОСЛЕ" (с индексами)

*   **`orders`**: Поиск по диапазону (`type: ref`) с использованием композитного индекса `idx_orders_user_id_created_at_id`. MySQL мгновенно находит все заказы пользователя и сразу получает их в отсортированном по `created_at` виде.
*   **`Extra`**: `Using index condition`. Сортировка (`filesort`) больше не нужна, так как данные уже упорядочены в индексе. База данных просто находит нужную точку и отсчитывает 45 строк (`OFFSET 30` + `LIMIT 15`), что чрезвычайно эффективно.

### Анализ 5: Подозрительные пользователи (`q5_suspicious.sql`)

**Запрос:**
```sql
-- Найти пользователей с более чем 3 неудачными платежами за определенный период
SELECT
    o.user_id,
    COUNT(p.id) AS failed_payments_count
FROM payments p
JOIN orders o ON p.order_id = o.id
WHERE p.status = 'failed' AND p.created_at BETWEEN '...' AND '...'
GROUP BY o.user_id
HAVING COUNT(p.id) > 3;
```

#### План "ДО" (без индексов)

*   **`payments` (`p`)**: Полное сканирование таблицы (`type: ALL`). Просмотрено **~72,000** строк для фильтрации по `status` и `created_at`.
*   **`orders` (`o`)**: Поиск по первичному ключу (`type: eq_ref`) для каждой строки из `payments`.
*   **`Extra`**: `Using where` для фильтрации и `Using temporary` для выполнения `GROUP BY`.

#### План "ПОСЛЕ" (с индексами)

*   **`payments` (`p`)**: Поиск по диапазону (`type: range`) с использованием индекса `idx_payments_status_created_at`. Просмотрено всего **~12** строк вместо 72 тысяч.
*   **`orders` (`o`)**: Поиск по первичному ключу (`type: eq_ref`).
*   **`Extra`**: `Using where` для фильтрации и `Using temporary` для `GROUP BY`. Временная таблица теперь создается для крошечного набора данных, что делает операцию очень быстрой.

## Вывод

Анализ наглядно доказывает, что правильно спроектированные индексы — это критически важный инструмент для оптимизации. Они позволяют базе данных избегать дорогостоящих операций полного сканирования таблиц (`Full Table Scan`), заменяя их на сверхбыстрый поиск по индексу. Это особенно важно для фильтрации (`WHERE`), соединений (`JOIN`) и сортировки (`ORDER BY`).
